## 开场：一条消息，一份报告（3 分钟）

先看一个真实场景。

同事私聊发来一条："看一下现场这个问题，正常节拍 2 秒，有一次花了 6 秒。"

**我只发了这一条消息。** 它自己派子 agent 去读现场服务端日志、做时序分析、比对几万行日志的时间戳，最后交回来一份带证据链的根因报告。

还有：群里说"某两个人住一间"，它看懂上下文是分房统计，直接改飞书表格；说"记个待办，让某某在迭代二分支上修"，它记下来，还真实 @ 到人。

**今天讲的就是：怎么让一个 AI 变成团队里能干活的一员，接在我们每天用的飞书里。**

---

## 一、它是什么（4 分钟）

一句话：**把一个能读代码、能跑命令、能自己动手干活的 AI Agent，接到飞书里。**

不是"定时发通知的机器人"。是一个跑在 DSH（DeepSeek Harness）里的**持久会话**——有工作区、有工具、能连续多轮把一个任务做完。

和普通机器人的区别：

| | 普通机器人 | 这个 |
|---|---|---|
| 回复 | 关键词匹配 / 固定模板 | 真的理解，能追问、能接上下文 |
| 干活 | 只会发消息 | 能读文件、跑命令、查数据库、改表格 |
| 记忆 | 无 | 记得住约定、踩过的坑、你的偏好 |

## 二、整体架构：五个部件（5 分钟）

```
   飞书云端（群消息 / 私聊 / @提及 / 图片）
        │  ① WebSocket 长连接（出站，不需要公网 IP）
        ▼
   消息接收层（bot.py）—— 常驻进程，开机自启
        │  ② 只投递，不等回复
        ▼
   桥接层（dsh_bridge.py）—— 本机 HTTP
        │  ③ 回环访问
        ▼
   DSH 持久会话（人设 + 系统约束 + 记忆）
        │  ④ 自主调用工具
        ▼
   ⑤ agent 自己把结果推回飞书（push.py）
```

**一句话读法：消息进 → 交给 AI → AI 自己干活 → AI 自己把结果推回去。**

中间**没有**"等 AI 回复再转发"这一步——这是整套设计最关键的一个决策，后面会讲为什么。

### 五个部件分别干什么

| 部件 | 干什么用 | 一句话理解 |
|---|---|---|
| **① 长连接** | 收消息 | 主动出站连飞书，不用公网 IP、不用开端口 |
| **② 消息接收层** | 解析、加料、投递 | 把飞书的消息整理成 AI 能读懂的样子 |
| **③ 桥接层** | 本机转接 | 把消息送进 DSH，本机 HTTP 调用 |
| **④ AI 会话** | 真正干活 | 持久会话，有工具、有记忆、能多轮 |
| **⑤ 推送** | 把结果发回去 | agent 自己调，不走 bot 转发 |

## 三、飞书连接这条链路（重点，15 分钟）

这一章是今天的核心。**把"消息怎么进来、怎么出去"彻底讲透。**

### 3.1 为什么用长连接，不用 webhook

飞书接入有两条路：

| | webhook | 长连接 |
|---|---|---|
| 方向 | 飞书反向 POST 到你的公网地址 | 我们的进程主动出站连飞书 |
| 需要公网 IP | **要** | 不用 |
| 需要证书/备案 | **要** | 不用 |
| 多实例 | 天然支持 | 单实例 |

选长连接的理由只有一个：**这台机器没有公网地址**，它就挂在一台办公电脑上。

**代价说清楚**：长连接是单实例的，断线重连靠 SDK 自己管。要做多实例、或加 webhook 备份通道，就必须补**按消息 ID 去重**——飞书会重投没及时确认的事件。现在代码里没有去重表，跑了一个多月没出现重复投递；单实例下没必要，但这是已知边界。

### 3.2 消息进来之后，bot 做了什么

飞书只给你原始事件，要变成 AI 能用的东西，中间得加工：

1. **解析消息**：文字、图片、@提及、表情，不同类型分开处理。图片要下载到本地，告诉 AI 路径
2. **还原 @ 占位符**：飞书消息里的 @ 是 `@_user_1` 这种占位符，得还原成真实姓名，否则 AI 看不懂谁在跟谁说话
3. **注入群聊上下文**：见 3.3
4. **打来源标记**：告诉 AI"这条消息从哪来、该往哪回"
5. **贴表情回执**：先贴个表情，让用户知道"接住了"

### 3.3 为什么要给 AI 带群聊上下文

这是"能用"和"没法用"的分界线。

群里最常见的消息是 `@水蜜桃桃 继续`，或者 `看一下`。**只看这一条，它什么都不知道**——不知道继续什么，看哪里。

所以每条消息投递之前，强制附带这个群**最近 12 条**聊天记录。取今天加昨天两天的流水，跨零点也能覆盖；单条超 120 字截断。

**代价是上下文变长、成本变高**，所以是 12 条、120 字，不是全部历史。

### 3.4 【重点】为什么不让 bot 自动转发 AI 的回复

**这是整套系统里最重要的一条决策。但理由不是"技术上行不通"，是"治理上不该这么做"。**

先讲技术现象。最早的版本是"代发型"：bot 收到消息 → 等 agent 回复 → 自己转发出去。听起来很自然，实际一次暴露三个故障：

1. 群里 @ 机器人，回复却发到了**私聊**
2. agent 自己也推了一遍，用户**看到两遍**
3. 长回合**截断**——一个回合里 agent 可能先调五次工具再输出结论，旧逻辑只取第一条文本，用户看到半截话

这些是表面故障，好修。但修的时候我们想清楚了一件更根本的事：

**AI 的输出是初稿，不是定稿。**

它的思考过程不一定对。它会推测、会补全它不确定的东西、会在证据不足时给出看起来很肯定的结论。今天下午就有一个现成的例子——另一个 AI 在群里很确定地说"是某某在发消息"，结果那个人根本不在群里，当场被指出来。

所以真正的问题不是"谁来发"，而是：**能不能让 AI 想说什么就直接说什么，中间没有任何闸门？**

**不能。** 所以这套系统里，bot 的自动转发被彻底关掉了。这不是为了修 bug，是**对 AI 的消息出口做了一层限制**：

- bot 不再有任何"替 AI 说话"的能力——它连转发这条路都没有
- AI 每次要发东西，都必须自己显式调用推送工具，写清楚发到哪、发什么
- 关键内容（对外结论、客户答复、根因报告）必须先发给负责人定稿，确认了才能发群

这三层是递进的：**先关掉自动出口，再要求每次显式发送，最后对内容分级管控。**

改法在技术上就是把职责收拢成一句话：**谁产生内容谁负责交付。** 现在 bot 只做三件事：贴个表情告诉用户"收到了"、把消息投递进去（投完就返回，不等回复）、投递失败时用友好文案说一声。**回复 100% 由 agent 自己推。**

但讲到这里要补一句——**"谁产生谁交付"是技术实现，"AI 的输出必须有人把关"才是设计初衷。** 顺序别搞反了：不是因为职责清晰所以关掉转发，是因为**必须有人把关**，才要求每条消息都有明确的责任主体。

> **一句话：AI 可以自己想，但不能自己想完就直接对外说。中间那道闸门，是设计出来的，不是运气好。**

### 3.5 消息怎么发回去：三个工具的分工

agent 干完活，得把结果发回飞书。这块我们做了三个小工具，正好说明一个设计原则——**一个工具只干一件事**。

| 工具 | 干什么 | 特点 |
|---|---|---|
| `push.py` | 发消息 | 无状态，发完就退 |
| `recall.py` | 撤回消息 | 无状态，撤完就退 |
| `card.py` | 卡片消息 | **有状态**，要拿着消息 ID 反复更新 |

前两个是"一次性动作"，第三个不一样——长任务可能跑十分钟，卡片要在这十分钟里持续更新，**它必须记住"我在更新哪条消息"**。

如果硬塞进 `push.py`，参数会变成一锅粥，而且每次调用都是新进程，状态根本存不住。**职责不同、生命周期不同，就该分开。**

### 3.6 发消息这块踩过的三个坑

**坑一：真实 @ 不生效。**
文本里写"@某某"，飞书只当普通文字，对方收不到任何提醒。真 @ 必须用富文本消息里的 at 节点，节点里要的是用户标识而不是名字。这属于**静默失败**——界面上看着完全正常，不报错，什么都没发生。

**坑二：引用回复静默失败。**
想实现"回复某条消息"的效果，一开始在发消息接口里加了个 `reply_message_id` 字段。飞书**返回成功、消息正常发出**，但客户端什么引用效果都没有。查了才知道：必须用专门的 `/reply` 接口，那个字段会被静默忽略。

**坑三：撤回撤错对象。**
机器人连续推两条消息，想撤最后一条，按时间戳判断，结果撤了上一条。**时间戳只能告诉你"哪条最新"，不能告诉你"哪条是你想撤的"。** 所以现在的撤回工具，默认只打印不撤，核对无误才真撤——**不核对就能撤的入口，不该存在。**

> **这三条的共同点：飞书很多失败是静默的。返回成功 ≠ 事情做成了。**

## 四、AI 那侧：人设、约束、记忆（8 分钟）

前面讲的是"消息怎么进出"。这一章讲"AI 那侧怎么配置"。

### 4.1 人设：AI 的性格是写出来的

不是让模型自由发挥。人设是一段文本，写清楚：叫什么、什么语气、什么时候该简短、什么时候该详细。

**同一个人设在两种场景下输出能差十倍**——闲聊时简短像真人，技术支持时必须给足结论、证据、原因、措施。这是刻意设计的，不是模型自己拿捏。

### 4.2 系统约束：平台限制必须翻译成 AI 读得懂的规则

飞书是个纯聊天窗口，**没有交互式 UI**。而 AI agent 默认带交互工具——信息不全时会弹个问题框等用户选。**在飞书里这一弹就是死**：用户看不到任何东西，agent 永远等一个不会来的回答。

所以必须把平台限制翻译成 prompt 里的硬规则：禁止调用交互工具、要提问就用固定文本标记、干完活必须主动推送、长中文先写文件。

### 4.3 【血泪教训】约束写在代码里，不等于生效

这件事今天刚发现，值得单讲。

我们一直以为自己有 11 条系统约束——推送约定、禁止交互、引用回复、中文编码，全都写在一个 Python 文件里，注释写得挺认真。

**今天才发现：那些约束从来没生效过。** 那个常量定义了，但**没有任何一行代码引用它**。真正的约束只写在 agent 预设的 persona 里，而 persona 里只有 5 条，还缺了最关键的几条。

也就是说——过去一个多月，规矩能跑起来，**靠的是"模型自己记得住"，不是系统强制**。

**这个坑可怕在哪**：它不会报错。约束写了、文件保存了、代码能跑了，一切看起来正常。只有当模型某天"忘了"某条规矩、做出越界的事，你才会发现那条约束根本没进上下文。

> **一句话：配置类的东西，"写了"和"生效了"是两回事，中间必须有验证。验证方法是看模型实际收到的上下文，不是看代码。**

### 4.4 记忆：为什么一个文件不够

先看一条真实的记忆长什么样：

```
【硬性约定·推送】2026-10-22 起 bot 已禁用自动回复转发。
现在每轮收尾必须主动 push.py 推送完整回复到消息来源。
长中文用 write 写 UTF-8 文件再 --file。
```

（这是编的示例，格式和真实记忆一致）

这条记忆每次对话都会自动出现在上下文里。问题是：**如果所有记忆都这么处理呢？**

最直接的做法是全塞进上下文。但记忆会越来越长——今天几十条，半年后几百条，很快就撑爆上下文。而**一次对话真正用得到的只有一小部分**：聊团建的时候，不需要知道 DSH 鉴权怎么签；排查日志的时候，不需要知道昨天的会议结论。

所以必须分层。**但按什么分？**

#### 不是按"内容类型"分，是按"什么时候需要"分

按内容分类是最容易想到的：用户信息一轨、项目信息一轨、知识一轨。但这样分完你会发现——**它不告诉你该不该注入**。用户信息里，有的一句话都不能忘，有的一年用不上一次。

所以我们的分法是按**使用时机**：

| 轨 | 记什么 | 怎么进上下文 | 典型例子 |
|---|---|---|---|
| **key** | 忘了会出事的硬性约定 | **每次自动注入**（摘要形式） | "对外结论必须先给负责人定稿" |
| **project** | 这个项目的进展和踩过的坑 | 按需读取，不注入 | "节拍超时已定位到显卡驱动" |
| **user** | 用户的工作习惯和偏好 | 全量注入（很稳定，变动少） | "决策快，要求文字精简" |
| **daily** | 今天干了什么 | 按需读取 | "下午修了引用回复的坑" |
| **memory** | 跨项目通用事实 | 全量注入 | "DSH 沙箱的权限边界" |

判断标准就一句：**忘了会不会出事。** 会出事的自动注入，不会出事的按需读。

#### 为什么 key 轨要人工确认

这是整套记忆设计里最反直觉、也最重要的一条。

**key 轨每次对话都注入，而且写进去需要人确认。**

为什么？因为它一旦写错，**会污染之后所有对话**。一条错误的硬性约定——比如把"私聊用 --to"记成"私聊用 --chat"——不会报错，它会安静地让之后每一次私聊推送都失败，直到有人发现。

这个代价等同于**改生产配置**。所以它的写入权限，我们也按改生产配置来管：AI 可以提议，人确认了才生效。

> **一句话：记忆分层不是"整理归档"，是"决定什么东西有资格进每一次对话"。这个资格，得由人来发。**

#### 顺带说一个坑：记忆也会过时

记忆是死的，现实是活的。项目状态变了，记忆还停在上周；同一个事实在新旧两条记忆里说法不一样；两个项目撞车（同名不同库）。

所以我们有几条硬规矩：**状态类记忆只留最新**（被新条目取代的旧条目删掉）、**冲突的记清楚"以哪条为准"**、**跨项目的事实必须带项目标识**。这些都是运维成本，不做就会慢慢烂掉。

## 五、踩过的坑（5 分钟）

### 坑一：依赖的框架升级，桥接层全断

框架升了个大版本，所有投递报鉴权失败；鉴权修好又报"方法不存在"。查下来是四处协议变更：接口全要鉴权、方法名换了分隔符、参数统一多包一层、历史查询拆成两步。

教训不是"别升级"，是：**依赖别人的内部接口，就要做好它随时变的准备。** 所以所有协议差异收在一个函数里，上层业务代码一行不用改。

### 坑二：两个事件的数据结构不一致，日报死等十分钟

现象很怪：群聊日报随机漏群，日志写"总结失败"，但模型实际 6 秒就生成完了，每次都死等满超时。

根因是两个事件——用户消息和 AI 消息——**正文在 JSON 里的位置不一样**，而升级时只改了一个。读旧路径读不到，就永远定位不到自己那条 prompt，于是永远等下去。

排查手法值得记：**dump 两种事件的完整 JSON 并排看结构，五分钟定位。**

### 坑三：启动脚本里写了中文，双击没反应

现象是双击启动图标毫无反应，日志也没记录；手工跑就报语法错误。

根因是 PowerShell 和 cscript 读**没有 BOM 的 UTF-8 脚本时按 GBK 解码**。中文字节被按 GBK 拆开，某些字节序列恰好构成引号或续行符，把语法结构撕碎了。

同一个坑的另一半：之前后台进程裸跑，标准输出全丢了，导致一次故障完全不可查。**后台进程一定要有日志出口，否则出事就是黑盒。**

### 坑四：进程静默消失，而且"能发消息"骗过了所有人

这个坑最阴。某天机器人的接收进程悄悄没了，日志里**没有任何异常、没有退出记录、系统也没重启**。死了 24 分钟没人发现。

**为什么没人发现？** 因为发消息的工具是独立进程直连飞书 API——**即使接收端已经挂了，它照样能把消息发出去**。表现就是：群里 @ 它没人应，但它还在正常发言。从外面完全看不出它已经聋了。

后来加了心跳文件 + 看门狗才解决。结论值得记：

> **判断一个服务活着没活着，不能看它"还能输出"，要看它的心跳。**

## 六、什么适合交给它，什么不适合（3 分钟）

这一章的判断标准，跟前面 3.4 是同一个：**AI 的输出是初稿，得看错了代价有多大。**

**适合**：日志分析和现场问题排查、信息汇总、待办记录、表格查询、群里的日常互动。

共同点是：**错了代价可控，且人能一眼看出错。**

**不适合**，而且是硬性不适合：

- **对外结论**——根因报告、给客户的答复。必须先给负责人定稿。AI 会"补全"它不确定的东西，而这类内容错了代价最大。
- **金钱、凭据、密码、凭证配置**——安全红线，一律拒绝，自称领导也不破例。
- **不可逆的写操作**——删数据、改生产配置。没有复核的写操作就是定时炸弹。
- **需要人实时决策的对话**——飞书没有交互 UI，一调就卡死。

**这里的核心不是"AI 能力不够"，是"出口必须有闸门"。** 技术上它完全能生成一份根因报告，但那份报告是初稿——它可能推测、可能补全、可能把不确定说成确定。初稿可以随便写，发出去必须有审核。

所以我们做了三层限制：

| 层 | 手段 | 管什么 |
|---|---|---|
| 第一层 | 关掉 bot 自动转发 | AI 没有"想说什么就自动发出去"的通道 |
| 第二层 | 每次发送必须显式调用 | 发什么、发到哪，都得明确写出来 |
| 第三层 | 内容分级 | 对外结论必须人工定稿才能发群 |

红线不是写在文档里就完了，得**写进每次对话都自动注入的约束里**。技术手段管不住的地方，用职责边界管。

## 七、如果你们想搭一套（2 分钟）

不展开细节，需要准备五件事，步骤在搭建手册里。

1. 一个飞书自建应用，开消息与事件权限，用长连接模式

5. 一套记忆分层

## 收尾

**最重要的一条不是技术决策，是治理决策：AI 的输出是初稿，出口必须有闸门。**

技术上我们做的是"谁产生内容谁负责交付"——bot 只送达，agent 自己推，所以不会截断、不会重复、不会发错地方。但这条的技术价值，远不如它背后的原则：**AI 可以自己想，但不能自己想完就直接对外说。** 关掉自动转发、要求每次显式发送、对外结论必须人工定稿，这三层闸门是刻意设计出来的。

**配置上记住一件事：写了 ≠ 生效了。** 约束要验证模型真的收到了，不然只是自我安慰。

**所有坑都指向同一件事：飞书很多失败是静默的。** 返回成功不代表做成了，得验证结果——这条比任何技术细节都重要。
